## 已有稳定性保障

- 原始历史、发送视图、最后实际主请求快照和累计用量分开；压缩不删除用户原文。
- 工具调用 / 结果按闭合组处理；停止、来源 / 授权变化、容量不足时不发布半份摘要。
- 多段摘要在内存准备，经过来源与版本复核后在短事务内发布一次；网络请求不跨数据库写事务。
- 摘要网络重试有独立生命周期，受一次准备 120 秒、单请求 60 秒和整轮预算共同限制；为最终回答预留输出和时间。
- 可用完整候选或完整原视图在满足硬窗口时允许回退；不把非法 / 截断摘要作为成功结果。
- 已受理失败保留错误与身份；未发请求不污染上一实际窗口，成功压缩提示能从状态及历史恢复。

这些机制已有本地 HTTP、SQLite、取消、重启恢复等测试覆盖。具体基线见 [QA](qa.md#1-代码审核修正2026-11-17)。

## 修复前主要发现

### 1. 优先处理：主回答请求超窗没有减量恢复

源码：AiService.java:1632、AiRetryPolicy.java:27、AiUpstreamException.java:39、ContextCoordinator.java:193。

摘要请求收到 context_length_exceeded 时会进入减量分片；主请求只走通用重试判定，HTTP 400 的窗口超限不会触发压缩后重发。TokenEstimator 采用字符权重估算，10% 安全余量并不构成真实供应商窗口保证。

本地故障探测 main_overflow：准备两轮合法历史，第一次主请求返回 HTTP 400 / context_length_exceeded，后续请求原本配置为成功。实际主请求 1 次、摘要 0 次、状态 FAILED / REQUEST_FAILED，没有自动恢复。

建议增加有界的主请求超窗恢复：仅处理明确、尚无输出 / 工具执行的窗口拒绝，在同一轮缩小发送目标、重新压缩与复核后继续。不能把固定正文的普通网络重试当作此恢复，也不能重复执行已成功工具。若当前输入等受保护内容本身过大，明确终止。

### 2. 优先处理：摘要输出截断缺少恢复策略

源码：ContextCoordinator.java:487、514；AiService.java:1830。

格式无效可修复一次，但 length / max_tokens 返回 CONTEXT_SUMMARY_INCOMPLETE，不进入修复或减量摘要路径。拒绝截断摘要是正确的数据保护；问题在于原视图已硬超窗且没有完整候选时，本轮直接失败。

本地故障探测 summary_truncated：8 轮长历史，首次摘要返回长度截断，若继续调用则会返回完整合法摘要。实际摘要 1 次、主请求 0 次、状态 FAILED / CONTEXT_SUMMARY_INCOMPLETE，没有发布检查点。

建议在剩余时间 / 输出预算内，针对截断采用有界的输出分配调整或更小的摘要批次，仍保留完整来源；不能拼接半份 JSON 后宣称成功。慢供应商是否容易达到当前 60 / 120 秒限制，需实测后再决定是否调整。

### 3. 长任务设计限制：全部回执不断累积进模型摘要

源码：ContextCoordinator.java:155、459、529；ContextSummary.java:12。

每次摘要都要求完整照抄此前 receipts 和本次回执，摘要输出却最多 4,096 Token；receipts 还存在 1,024 项结构上限。不同轮次 / 调用的回执通常不会被集合去重消除，因而规模持续增长。

本地构造 200 个示例回执，即便目标仅两个字、其他内容数组全部为空，最小 JSON 按应用自己的估算器已达 4,131 Token。该数值用于说明预算矛盾，不能把 200 次操作当作所有模型统一的实际失败临界值。

建议把完整回执作为应用确定性台账保存和校验，模型视图只携带当前续接所需的简洁操作状态；不要要求语言模型在每次滚动压缩时重新抄写所有历史 ID。仍须保留来源、授权和已执行操作核对能力。

### 4. 已验证的校验边界：合法 JSON 可以遗漏关键旧约束

源码：ContextCoordinator.java:201、289、514；ContextSummary.java:9。

校验能够拒绝伪造来源、遗漏回执、非法结构，却无法确认 constraints / decisions / pending 是否完整。来源字段允许合法子集（包括空集合）；coverage 由应用按实际送入摘要模型的来源建立，不代表这些来源的重要信息被保留。

本地故障探测 semantic_loss：旧用户消息包含“禁止自动写入笔记，只允许列出建议。”；夹具确认该约束确实被送入摘要请求，但故意返回结构合法、所有内容数组为空的摘要。结果为 COMPLETED，检查点已发布，最终主请求不含该约束。

这证明缺少信息保留保证，不证明真实模型经常这样做，也不代表本次发生了未经授权写入。建议优先建立小规模多次压缩评测，检查用户否定 / 改口、精确数字、未完成任务和确认写入状态；对关键持续约束保留带来源、可失效的独立状态，避免仅依赖递归摘要。不能用简单的来源集合相等代替语义验证。

### 5. 代码确认的规模限制：覆盖历史仍占扫描预算

源码：ConversationProjection.java:49、219；ChatHistoryRepository.java:56、85。

历史读取会取出原始正文 / 密文字段，并在检查 generation、墓碑及摘要覆盖之前累计字节。已有摘要覆盖的旧轮次虽然不解密，仍计入 32 MiB、16,384 轮及 30 秒扫描保护；每次请求仍从当前截止点向旧历史扫描。

因此，模型发送窗口已很小也不能保证超长本地会话可继续：仍可能触发 CONTEXT_SCAN_LIMIT。此项由当前源码顺序和查询确认，本次没有生成超大数据库测性能，也没有测出实际延迟。

建议先按身份 / 来源版本校验覆盖元数据，仅加载未覆盖记录的正文；保留对未读内容的明确保护，不能简单移除扫描上限或静默丢弃历史。检查点来源数量本身也有 4,096 项上限，后续需要可扩展的覆盖表示。

## 修复前判断与建议顺序

| 维度 | 当时判断 |
|---|---|
| 原历史、来源和存储完整性 | 本地工程保证较扎实，失败通常能安全终止 |
| 取消、错误保留、状态恢复 | 已有回归覆盖；上一轮修正已验证 |
| 请求超窗、摘要截断后的自动续接 | 有已复现缺口，优先补齐 |
| 多轮压缩的信息保留 | 尚无真实模型质量证据；对抗夹具确认结构校验不足以保证 |
| 大量写操作 / 超长本地历史 | 存在累积回执和全历史扫描的规模限制 |
| 实际成功率、P95 等待时间、缓存收益 | 未测量，不能给百分比或性能承诺 |

建议先修复主请求超窗恢复和截断摘要恢复，再处理回执与历史扫描扩展，同时用少量真实模型样例验证反复压缩的信息保留。现有四层数据分离与原子发布机制可以保留，无需推翻重写。
